# EIP-712 sur un Ledger : ce que l'appareil affiche vraiment

Ce document raconte une seule expérience, menée jusqu'au bout, et ce qu'elle a appris. Tout ce
qui suit a été observé — les commandes qui le reproduisent sont à la fin.

---

## 1. Pourquoi le nombre doit être sur l'appareil

La garde de TARE intercepte un swap Uniswap v4 **avant** la signature et annonce ce que le hook
du pool prélève. Si ce nombre n'apparaît que dans la page, il ne prouve rien : une page se
repeint. Un logiciel malveillant qui contrôle l'onglet contrôle aussi le chiffre affiché.

**Le seul endroit où un nombre engage quelque chose, c'est l'écran du portefeuille matériel.**
C'est un écran que le navigateur ne peut pas atteindre.

D'où la question : peut-on faire afficher **nos** champs — pas une transaction générique, mais
`take 689.95 bps` — sur un Ledger ?

---

## 2. Le message

Un EIP-712 dont chaque champ est un constat de la garde. Type principal `TareGuardApproval` :

```
verdict          BLOCK
hook             0x1aEA38f06deCE45c252eF1Ac5AF989D51Dc8E8cc
poolId           0xD996FF76787C7C520483FE0164699395CC89BFCB6FC4BDBA282…
take             689.95 bps
label            MEASURED
size             100000000000000 en entree
direction        1->0
measuredAtBlock  50614000
dataset          125072 mesures, 112 hooks, 7817 pools, chaine 8453,
                 moteur tare-engine/0.3.0, stub 0x8e39b2ad…
freshness        mesures au bloc 50614000 ; bloc courant non fourni, retard inconnu
warnings         aucun
promptDigest     0x7CA143E05DC7F4A9A27E22CD8A8ABDF95A20B090601D17599D…
```

Trois choix méritent d'être expliqués.

**`take` est une chaîne, pas un nombre.** `689.95 bps` avec son unité, parce qu'un `uint` sur un
écran de Nano ne dit pas s'il s'agit de points de base, de centièmes, ou de wei.

**`label` voyage avec la valeur.** Un `take` sans son étiquette laisserait croire qu'une absence
de mesure vaut zéro. Sur l'appareil comme ailleurs, `NOT_MEASURABLE` n'est pas `0.00`.

**`promptDigest` scelle le texte montré à l'humain.** La signature n'atteste pas seulement des
champs : elle atteste **la phrase exacte** que la garde a affichée.

## 3. L'expérience

Pas un appareil physique : **Speculos**, l'émulateur que Ledger publie précisément pour ça,
faisant tourner l'**application Ethereum officielle 1.22.3** pour Nano X, téléchargée depuis les
releases de `LedgerHQ/app-ethereum`. Même binaire, même code d'affichage.

Le transport se connecte. L'appareil répond à `getAddress` :
`0xDad77910DbDFdE764fC21FCD4E74D71bBACA6D8D`.

### Premier essai — le mur

Avec `fullImplem: true`, qui demande le chemin d'affichage **filtré** :

> **Blind signing must be enabled in settings**

Statut `0x6a80`, *invalid data received*.

L'application ne sait étiqueter les champs d'un EIP-712 arbitraire que si elle possède des
**descripteurs de filtre** pour ce schéma — la métadonnée de signature claire que Ledger publie
par type de message. `TareGuardApproval` est le nôtre, Ledger ne l'a jamais vu.

### Le piège

L'instruction à l'écran dit d'activer **Blind signing**. C'est le mauvais réglage, et l'activer
aurait détruit exactement ce qu'on cherchait : le blind signing fait signer **un hash**, sans
aucun champ.

Notre code refuse ce chemin. `packages/guard/src/ledger.ts:20` : **aucun repli**
`signEIP712HashedMessage`. Une garde qui échoue en « oui » ne garde rien.

### Le bon réglage

En parcourant les réglages de l'application, écran par écran :

```
Blind signing     Enable transaction blind signing        Disabled
Nonce             Display nonce in transactions           Disabled
Raw messages      Displays raw content of EIP712 messages Disabled   <---
Debug contracts   Display contract data details           Disabled
Smart accounts    Enable EIP-7702 authorizations          Disabled
```

**« Raw messages »** — activé, et avec `fullImplem: false`, l'appareil affiche **seize écrans** :

```

poolId (1/2) 0xD996FF76787C7C52 0483FE0164699395CC 89BFCB6FC4BDBA282
poolId (2/2) 0771F127FA300
take 689.95 bps
label MEASURED
size 100000000000000 en entree
direction 1->0
dataset (1/3) 125072 mesures, 112 hooks, 7817 pools, chaine 8453, moteur
dataset (2/3) tare-engine/0.3.0, stub 0x8e39b2ad4344342
dataset (3/3) b4f7dc5cf31df0aec9b d5b5f8ec7fccd241256 cf1fda637a4
```

**Signature rendue : `v=28`.** La capture brute, non retouchée, est dans
[`docs/ledger/ECRANS.md`](docs/ledger/ECRANS.md).

## 4. Ce que ça prouve, et ce que ça ne prouve pas

**Prouvé.** Le message typé atteint l'appareil, l'appareil affiche **chaque champ étiqueté**, un
humain lit `take 689.95 bps` sur un écran que la page ne contrôle pas, et la signature est
cryptographiquement réelle.

**Non prouvé.** Aucun appareil physique. Speculos fait tourner le même binaire et le même code
d'affichage — c'est pourquoi Ledger le publie — mais un émulateur n'est pas un Nano dans une main.
Et surtout : notre transport de production est **WebHID**, tandis que Speculos passe par
HTTP/APDU. Le chemin `openWebHidDevice` n'est donc **pas** exercé. Une dizaine de lignes que dix
minutes avec un vrai appareil couvriraient.

---

## 5. Le manque, et il tient en une phrase

Le réglage par défaut est un choix défendable : ne pas afficher n'importe quel EIP-712 brut
protège l'utilisateur ordinaire.

**Ce qui ne l'est pas, c'est l'instruction.** Un développeur qui rencontre *« Blind signing must be
enabled in settings »* active le blind signing, obtient un hash à l'écran, et conclut que la
signature claire est indisponible pour les schémas personnalisés. **Elle est disponible.** Le
message l'envoie sur le mauvais bouton, et rien n'y mentionne « Raw messages ».

Ce sera vrai pour chaque outil de sécurité qui voudra ses chiffres sur l'appareil plutôt que dans
la page — c'est-à-dire pour tous.

**La contribution proposée est une phrase à corriger, pas une fonctionnalité à construire** :
quand un EIP-712 ne peut pas passer par le chemin filtré, le dire, et nommer **Raw messages**
comme le réglage qui l'affiche brut. `app-ethereum` pour le texte de l'écran, `ledgerjs` pour
remonter la cause au lieu d'un `0x6a80` nu.

**NON VÉRIFIÉ, et volontairement non affirmé** : nous n'avons pas parcouru la procédure de dépôt
des descripteurs chez Ledger, donc nous ne la décrivons pas.

Ce qui manquait à **Speculos** : rien. Il a émulé fidèlement, exposé les écrans en HTTP, et laissé
piloter les boutons. C'est grâce à lui que tout ceci s'énonce au lieu de se supposer.

## 6. Reproduire

```bash
curl -sL https://github.com/LedgerHQ/app-ethereum/releases/download/1.22.3/app-1.22.3-nanox.elf \
  -o eth.elf
docker run -d --name speculos -p 5010:5000 -v "$PWD":/apps \
  ghcr.io/ledgerhq/speculos:latest --model nanox --display headless --api-port 5000 /apps/eth.elf

# Reglages -> Raw messages -> Enabled : presser, lire, decider
curl -s  "http://127.0.0.1:5010/events?currentscreenonly=true"
curl -sX POST http://127.0.0.1:5010/button/right -d '{"action":"press-and-release"}'

cd packages/guard && npm i --no-save @ledgerhq/hw-transport-node-speculos-http
# puis : buildGuardTypedData(report) -> eth.signEIP712Message(path, typed, false)
```

`fullImplem: false` est décisif. `true` demande le chemin filtré — celui qui n'a pas de
descripteurs pour notre schéma, et qui produit le message trompeur.
