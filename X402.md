# x402 on Hedera — the toll, crossed

`EIP712.md` tells the story of the signature. This one tells the story of the **payment**:
what it took for a TARE request to be settled for real, in USDC, on Hedera testnet — and
the three defects that only a real settlement could show.

---

## Why a toll, and why priced per measurement

TARE sells one precise thing: **a measurement**. A measurement is a pair of quotes for the
same swap, once with the hook, once with an inert 89-byte stub substituted for its
bytecode. The gap *is* what the hook takes.

A request that asks for five sizes is therefore worth **five** measurements — five forks
queried, five pairs of quotes, five lines in the ledger. Billing it as a single one would
be wrong in both directions: too expensive for whoever asks for one measurement, free for
whoever asks for ten.

So the price is not a constant in a config file. It is **computed from the request body,
before any payment** ([`x402.ts`](apps/api/src/x402.ts), `price` field), and the 402
announces it before anyone has signed anything.

## The protocol, in four visible steps

The client ([`apps/api/src/pay/client.ts`](apps/api/src/pay/client.ts)) does not decorate
`fetch`. It makes both calls by hand, so that the protocol can be **seen**:

```
1. POST /measure  with no payment
   -> 402 + accepts[] : { scheme:"exact", network:"hedera:testnet",
                          amount:"5000", asset:"0.0.429274",
                          payTo:"0.0.10367997", extra:{ feePayer:"0.0.7162784" } }

2. createPaymentPayload()
   -> a Hedera TransferTransaction signed PARTIALLY by the payer.
      The facilitator will add its fee payer signature to it: it is the
      facilitator that pays the network fees, not the client.

3. POST /measure  with PAYMENT-SIGNATURE (3,272 bytes)
   -> 200 + PAYMENT-RESPONSE { success:true, transaction:"0.0.7162784@...",
                               payer:"0.0.10367920", network:"hedera:testnet" }

4. re-read on the mirror node
   -> SUCCESS, and the transfer itself: 0.0.10367920 -> 0.0.10367997
```

**Step 4 is not decorative.** The project's hard rule no. 3, applied to payment: a 200 says
the server returned the resource, not that a transfer took place. As long as the mirror
node has not returned the transaction, the state is `NOT_VERIFIED` — never promoted.

## The real settlements

Two examples, re-read on the network, taken from
[`docs/x402-settlements.jsonl`](docs/x402-settlements.jsonl) (append-only: a file that gets
overwritten is not a trail):

| request | units | charged | transaction | consensus |
|---|---|---|---|---|
| 5 sizes, direction 1→0 | 5 | **5,000** units (0.005 USDC) | `0.0.7162784@1788839677.057914627` | `1788839684.510784526` |
| 1 size, direction 1→0 | 1 | **1,000** units (0.001 USDC) | `0.0.7162784@1788839762.263656678` | `1788839770.431335104` |

Same route, same request shape, **five times the price because five measurements were
asked for**. That is what *compute metering rather than a flat per-request charge* means —
and it is only verifiable because the money moved.

Network fees observed: **1,332,052 tinybar** per settlement, paid by the facilitator.
HCS message: ~**364,000 tinybar** (0.0036 HBAR).

The HCS log, once the settlement has been attached:

```json
{"v":"tare.metering.v1","batch":"b_e175d45c5ef847e297d4","ts":"2026-09-08T03:54:43.063Z",
 "digest":"sha256:f3615520ea525dc14dc44392443feac365f6230473b971fe30d9c11c3863bb18",
 "units":5,"unit_price_usd":0.001,"amount_usd":0.005,"payer":"0.0.10367920",
 "settlement":"0.0.7162784@1788839677.057914627","block":50614000}
```

That is what a *verifiable payment audit trail* is: the digest of the batch, its payer, its
settlement hash, timestamped by Hedera consensus — and re-read on the mirror before being
declared published.

## The three defects that the first real payment showed

The toll had existed for weeks. It answered 402, it announced its price, its tests passed.
**Nobody had ever crossed it.** Here is what was wrong.

### 1. The server was reading the wrong header

x402 v2 sends **`PAYMENT-SIGNATURE`**; only v1 used `X-PAYMENT`. The server read only the
latter. The toll worked anyway — it is the library that verifies, and it reads both
([`server/index.js:3012`](apps/api/node_modules/@x402/core/dist/cjs/server/index.js))
— but **the whole rest of the service saw the request as unpaid**:

- the ledger attributed the units to `"(non paye)"`;
- a "no payment, therefore no settlement hook" branch anchored the batch on HCS
  **before** the settlement, with `payer: null, settlement: null`;
- then the settlement hook anchored it a second time. Two messages for one batch: an
  audit trail where you have to choose which of the two lines is authoritative is no
  longer a trail.

### 2. The settlement was attached to nothing

The x402 hash arrives **after** the handler: the middleware verifies, lets the request
through, then settles. The batch, for its part, is written **during** the handler. The
thread between the two was a `let lastBatchId` shared by the whole server — and it was
only assigned on the **failure** path. A successful batch was therefore never attached:
`settlement_tx: null` on a transaction that was nonetheless confirmed on-chain. Being
shared, it would moreover have attributed one request's settlement to another request's
batch as soon as two clients pay at the same time.

Replaced by an `AsyncLocalStorage`: one slot **per request**, which the hook finds again
because it runs in the same asynchronous context. No race, no assumed ordering.

### 3. `anchorBatch` was not called anywhere

The `README` of batch G described the wiring (`void metering.service.anchorBatch(receipt)`)
and nobody had done it. The HCS topic existed, the CLI command worked, but **no served
batch had ever gone to it**. It is now called from the settlement hook — *after* the
attachment, not before, otherwise the digest would leave with `settlement: null` and the
log would no longer be a *payment* audit trail, just a compute timestamp.

## The honesty gap: paying in advance for what will be declared non-billable

A project rule says: *"A `NOT_MEASURABLE` measurement is not billed. We do not bill a
silence."*

The first real payment put it at fault. x402 collects **before** the engine runs:

```
402: the price is fixed  ->  settlement: the money moves  ->  engine: the label exists
```

The first settled request asked for the `0->1` direction of a pool for which that direction
is in *custom accounting*: verdict `NOT_MEASURABLE`, honest and correct. The ledger wrote
`billable: false, amount_usd: 0`. **And 0.001 USDC had indeed been charged.**

Saying `amount_usd: 0` presented as free what had been taken. So the service now keeps
three figures instead of one:

| field | what it says |
|---|---|
| `amount_usd` | what is **owed** — the billable units |
| `amount_settled_usd` | what was **actually** charged on-chain |
| `credit_usd` | the gap: what the service **owes** |

```json
{ "units_recorded": 1, "units_billed": 0,
  "amount_usd": 0, "amount_settled_usd": 0.001,
  "credit_units": 1, "credit_usd": 0.001 }
```

A non-billable unit that has already been paid for is not free: it is a **credit**, never a
zero. Five tests pin this contract
([`service.test.ts`](apps/api/src/metering/service.test.ts), section *le premier
reglement reel*).

## The faucet trap, for the next person

Paid for at the price of an hour lost, and written here so that person does not lose it
again.

The [Circle faucet](https://faucet.circle.com) is **public and account-free**: 20 testnet
USDC per address per 2 h window, Hedera Testnet in the list of networks.

- It wants the **Hedera ID** (`0.0.10367920`). The EVM address of the same account is
  rejected: *"Please enter a valid wallet address for Hedera"*.
- And above all: **if the account is not associated with the token, it answers "Tokens
  sent" and nothing arrives.** No error, no message, no transaction on the mirror. The
  request is consumed; you have to wait 2 h.

`max_automatic_token_associations: -1` on the account **is not enough** here. An explicit
`TokenAssociateTransaction` is required, **before** the request:

```bash
cd apps/api
npx tsx src/pay/cli.ts associer payeur
npx tsx src/pay/cli.ts associer encaisseur
npx tsx src/pay/cli.ts solde         # check BEFORE asking the faucet
```

```bash
docker compose up -d anvil            # the pinned fork, block 50614000
cd apps/api && npx tsx src/server.ts  # the API, toll active

# one measurement, settled for real
TARE_POOL_ID=0x… TARE_SIZES='1000000000000' TARE_DIRECTIONS='1->0' \
  npx tsx src/pay/cli.ts payer

# five measurements: the price must be multiplied by five
TARE_SIZES='100000000,1000000000,10000000000,100000000000,1000000000000' \
  npx tsx src/pay/cli.ts payer
```

Each run appends a line to `docs/x402-settlements.jsonl`: the request, the price announced
in the 402, the settlement hash, what the mirror node says about it, and the balances
before and after.

## What is not proven

- **The toll is hosted; the engine behind it is not.** <https://api.tare-hooks.tech/measure>
  answers 402 with its price. The measurement engine (the pinned `anvil` fork) does not run on
  that host, so a fresh measurement is not delivered there yet, and the settlements above were
  made against a local run of the same service.
- **Testnet only.** Nothing has been settled in mainnet USDC.
- **A single facilitator.** `blocky402` is the only one tested; the code does not assume
  any other, but no other has been tried.
