# x402 sur Hedera — le péage, franchi

`EIP712.md` raconte la signature. Celui-ci raconte le **paiement** : ce qu'il a fallu
pour qu'une requête de TARE soit réglée pour de vrai, en USDC, sur Hedera testnet — et
les trois défauts que seul un règlement réel pouvait montrer.

---

## Pourquoi un péage, et pourquoi à la mesure

TARE vend une chose précise : **une mesure**. Une mesure, c'est un couple de cotations du
même swap, une fois avec le hook, une fois avec un stub inerte de 89 octets substitué à
son bytecode. L'écart *est* ce que le hook prend.

Une requête qui demande cinq tailles vaut donc **cinq** mesures — cinq forks interrogés,
cinq paires de cotations, cinq lignes au registre. La facturer comme une seule serait
faux dans les deux sens : trop cher pour qui demande une mesure, gratuit pour qui en
demande dix.

Le prix n'est donc pas une constante dans un fichier de config. Il est **calculé sur le
corps de la requête, avant tout paiement** ([`x402.ts`](apps/api/src/x402.ts), champ
`price`), et le 402 l'annonce avant que quiconque n'ait signé quoi que ce soit.

## Le protocole, en quatre temps visibles

Le client ([`apps/api/src/pay/client.ts`](apps/api/src/pay/client.ts)) ne décore pas
`fetch`. Il fait les deux appels à la main, pour qu'on **voie** le protocole :

```
1. POST /measure  sans paiement
   -> 402 + accepts[] : { scheme:"exact", network:"hedera:testnet",
                          amount:"5000", asset:"0.0.429274",
                          payTo:"0.0.10367997", extra:{ feePayer:"0.0.7162784" } }

2. createPaymentPayload()
   -> une TransferTransaction Hedera signée PARTIELLEMENT par le payeur.
      Le facilitateur y ajoutera sa signature de fee payer : c'est lui qui
      paie les frais réseau, pas le client.

3. POST /measure  avec PAYMENT-SIGNATURE (3 272 octets)
   -> 200 + PAYMENT-RESPONSE { success:true, transaction:"0.0.7162784@...",
                               payer:"0.0.10367920", network:"hedera:testnet" }

4. relecture sur le mirror node
   -> SUCCESS, et le transfert lui-même : 0.0.10367920 -> 0.0.10367997
```

**Le point 4 n'est pas décoratif.** Règle dure n°3 du projet, appliquée au paiement : un
200 dit que le serveur a rendu la ressource, pas qu'un transfert a eu lieu. Tant que le
mirror node n'a pas rendu la transaction, l'état est `NOT_VERIFIED` — jamais promu.

## Les règlements réels

Deux exemples, relus sur le réseau, tirés de
[`docs/x402-settlements.jsonl`](docs/x402-settlements.jsonl) (append-only : un fichier
qu'on écrase n'est pas une piste) :

| requête | unités | prélevé | transaction | consensus |
|---|---|---|---|---|
| 5 tailles, sens 1→0 | 5 | **5 000** unités (0,005 USDC) | `0.0.7162784@1788839677.057914627` | `1788839684.510784526` |
| 1 taille, sens 1→0 | 1 | **1 000** unités (0,001 USDC) | `0.0.7162784@1788839762.263656678` | `1788839770.431335104` |

Même route, même forme de requête, **cinq fois le prix parce que cinq mesures ont été
demandées**. C'est ce que veut dire *compute metering rather than a flat per-request
charge* — et ce n'est vérifiable que parce que l'argent a bougé.

Frais réseau observés : **1 332 052 tinybar** par règlement, payés par le facilitateur.
Message HCS : ~**364 000 tinybar** (0,0036 HBAR).

Le journal HCS, une fois le règlement raccroché :

```json
{"v":"tare.metering.v1","batch":"b_e175d45c5ef847e297d4","ts":"2026-09-08T03:54:43.063Z",
 "digest":"sha256:f3615520ea525dc14dc44392443feac365f6230473b971fe30d9c11c3863bb18",
 "units":5,"unit_price_usd":0.001,"amount_usd":0.005,"payer":"0.0.10367920",
 "settlement":"0.0.7162784@1788839677.057914627","block":50614000}
```

C'est ça, une *verifiable payment audit trail* : l'empreinte du lot, son payeur, son hash
de règlement, horodatés par le consensus Hedera — et relus sur le mirror avant d'être
déclarés publiés.

## Les trois défauts que le premier paiement réel a montrés

Le péage existait depuis des semaines. Il répondait 402, il annonçait son prix, ses tests
passaient. **Personne ne l'avait jamais franchi.** Voici ce qui était faux.

### 1. Le serveur lisait le mauvais en-tête

x402 v2 envoie **`PAYMENT-SIGNATURE`** ; seul v1 utilisait `X-PAYMENT`. Le serveur ne
lisait que le second. Le péage fonctionnait quand même — c'est la bibliothèque qui
vérifie, et elle lit les deux ([`server/index.js:3012`](apps/api/node_modules/@x402/core/dist/cjs/server/index.js))
— mais **tout le reste du service voyait la requête comme non payée** :

- le registre attribuait les unités à `"(non paye)"` ;
- une branche « pas de paiement, donc pas de hook de règlement » ancrait le lot sur HCS
  **avant** le règlement, avec `payer: null, settlement: null` ;
- puis le hook de règlement l'ancrait une seconde fois. Deux messages pour un lot : une
  piste d'audit où il faut choisir laquelle des deux lignes fait foi n'est plus une piste.

### 2. Le règlement n'était raccroché à rien

Le hash x402 arrive **après** le handler : le middleware vérifie, laisse passer, puis
règle. Le lot, lui, est écrit **pendant** le handler. Le fil entre les deux était un
`let lastBatchId` partagé par tout le serveur — et il n'était affecté que dans le chemin
d'**échec**. Un lot réussi n'était donc jamais raccroché : `settlement_tx: null` sur une
transaction pourtant confirmée on-chain. Partagé, il aurait de plus attribué le règlement
d'une requête au lot d'une autre dès que deux clients paient en même temps.

Remplacé par un `AsyncLocalStorage` : une case **par requête**, que le hook retrouve parce
qu'il s'exécute dans le même contexte asynchrone. Pas de course, pas d'ordre supposé.

### 3. `anchorBatch` n'était appelé nulle part

Le `README` du lot G décrivait le montage (`void metering.service.anchorBatch(receipt)`)
et personne ne l'avait fait. Le topic HCS existait, la commande CLI marchait, mais **aucun
lot servi n'y était jamais parti**. Il est maintenant appelé depuis le hook de règlement —
*après* le raccrochage, pas avant, sinon l'empreinte partirait avec `settlement: null` et
le journal ne serait plus une piste d'audit de *paiement*, juste un horodatage de calcul.

## Le trou d'honnêteté : payer d'avance ce qui sera déclaré non facturable

Une règle du projet dit : *« Une mesure `NOT_MEASURABLE` n'est pas facturée. On ne facture
pas un silence. »*

Le premier paiement réel l'a mise en défaut. x402 encaisse **avant** que le moteur ne
tourne :

```
402 : le prix est figé      ->  règlement : l'argent bouge  ->  moteur : l'étiquette existe
```

La première requête réglée a demandé le sens `0->1` d'un pool dont ce sens est en *custom
accounting* : verdict `NOT_MEASURABLE`, honnête et correct. Le registre a écrit
`billable: false, amount_usd: 0`. **Et 0,001 USDC avait bel et bien été prélevé.**

Dire `amount_usd: 0` présentait comme gratuit ce qui avait été pris. Le service tient donc
maintenant trois chiffres au lieu d'un :

| champ | ce qu'il dit |
|---|---|
| `amount_usd` | ce qui est **dû** — les unités facturables |
| `amount_settled_usd` | ce qui a **réellement** été prélevé on-chain |
| `credit_usd` | l'écart : ce que le service **doit** |

```json
{ "units_recorded": 1, "units_billed": 0,
  "amount_usd": 0, "amount_settled_usd": 0.001,
  "credit_units": 1, "credit_usd": 0.001 }
```

Une unité non facturable déjà payée n'est pas gratuite : c'est un **crédit**, jamais un
zéro. Cinq tests fixent ce contrat
([`service.test.ts`](apps/api/src/metering/service.test.ts), section *le premier
règlement réel*).

## Le piège du faucet, pour la personne suivante

Payé au prix d'une heure perdue, et écrit ici pour qu'elle ne la reperde pas.

Le [faucet Circle](https://faucet.circle.com) est **public et sans compte** : 20 USDC
testnet par adresse et par tranche de 2 h, Hedera Testnet dans la liste des réseaux.

- Il veut l'**identifiant Hedera** (`0.0.10367920`). L'adresse EVM du même compte est
  refusée : *« Please enter a valid wallet address for Hedera »*.
- Et surtout : **si le compte n'est pas associé au jeton, il répond « Tokens sent » et
  rien n'arrive.** Aucune erreur, aucun message, aucune transaction sur le mirror. La
  demande est consommée ; il faut attendre 2 h.

`max_automatic_token_associations: -1` sur le compte **ne suffit pas** ici. Il faut une
`TokenAssociateTransaction` explicite, **avant** la demande :

```bash
cd apps/api
npx tsx src/pay/cli.ts associer payeur
npx tsx src/pay/cli.ts associer encaisseur
npx tsx src/pay/cli.ts solde         # vérifie AVANT de demander au faucet
```

## Rejouer

```bash
docker compose up -d anvil            # le fork épinglé, bloc 50614000
cd apps/api && npx tsx src/server.ts  # l'API, péage actif

# une mesure, réglée pour de vrai
TARE_POOL_ID=0x… TARE_SIZES='1000000000000' TARE_DIRECTIONS='1->0' \
  npx tsx src/pay/cli.ts payer

# cinq mesures : le prix doit être multiplié par cinq
TARE_SIZES='100000000,1000000000,10000000000,100000000000,1000000000000' \
  npx tsx src/pay/cli.ts payer
```

Chaque exécution ajoute une ligne à `docs/x402-settlements.jsonl` : la requête, le prix
annoncé au 402, le hash de règlement, ce que le mirror node en dit, et les soldes avant
et après.

## Ce qui n'est pas prouvé

- **Le service n'est pas hébergé.** Tout ce qui précède tourne en local. Le track Hedera
  demande un service *en ligne* ; ce n'est pas fait.
- **Testnet uniquement.** Rien n'a été réglé en USDC mainnet.
- **Un seul facilitateur.** `blocky402` est le seul testé ; le code n'en suppose pas
  d'autre, mais aucun autre n'a été essayé.
